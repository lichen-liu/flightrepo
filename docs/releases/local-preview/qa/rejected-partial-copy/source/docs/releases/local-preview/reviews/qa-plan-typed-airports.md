## Input and semantics gate

The API, visible labels and documented examples must agree on these distinctions before final acceptance:

- **Direct code entry:** type or paste one three-letter ASCII IATA code; suggestions are optional assistance. Trim outer whitespace and normalize case. A syntactically valid code must not require membership in the limited suggestion catalog.
- **Required stop:** `via_airport` is a route requirement, not a ranking preference. It must be an intermediate airport distinct from the initial origin and final destination. Define whether arrival at, departure from, or either side of a permitted airport-change connection satisfies the stop. The recommended interpretation counts either intermediate airport actually used by the journey; mere membership in the same city does not satisfy it.
- **Next stop:** the recommended `next_airport` meaning is the destination of the immediately following flight after the retained prefix. It does not select the departure airport of that flight, and it does not constrain every later leg. Use an explicit label such as “Next stop” with explanatory text if needed. Final review will check the actual adopted definition.
- **Empty and invalid:** omitted or `null` optional constraints mean unrestricted. An empty optional UI control should produce that state, not a failed search. If the API rejects `""`/whitespace-only strings rather than normalizing them to `null`, document and test this deliberately. Required empty codes, digits, punctuation, non-ASCII letters, wrong lengths and non-string values must produce readable validation failures.
- **Unknown and unavailable:** valid syntax does not establish that an airport exists or that schedules are loaded. UTC queries may operate on exact codes outside the suggestion catalog. Airport-local origin/deadline entry still requires actual timezone metadata and an actionable missing-metadata error. A via/next stop does not itself require a timezone lookup merely to filter flight facts. Empty results must describe the reviewed dataset/search scope rather than assert no flight exists in the world.
- **Conflicts:** an avoided required stop, via equal to an endpoint, or an explicit `chosen_next` contradicting `next_airport` must have a declared outcome. Do not silently drop either instruction. Rejected choices must preserve the previous selected journey.

These are acceptance criteria inferred from the owner’s requested behavior and the existing architecture, not findings from observed customer sessions. The owner did not approve an exhaustive multi-stop constraint language through this feedback.

## Independent method and evidence requirements

Initial read-only inspection covered the route-search models/search/session, connection/rebuild contracts and planner, the reader’s snapshot-loading path, local-time request conversion, workspace form/editor/catalog flow, existing web/routing tests and browser harness. At this checkpoint the new implementation was still changing; only the new local-search `via_airport` field had appeared in the inspected snapshot. No final behavior claim is made from those intermediate bytes.

Final review should inspect actual source and fresh backend/frontend review receipts against the same manifest, not only trust asserted check counts. Use tiny deterministic graphs and HTTP request probes for TA03–TA11, an independent expected-path derivation for via/next behavior, and fresh browser assertions/captures for TA02 and TA12–TA15. Tests should include counterexamples where the old unconstrained search would produce the wrong limited answer. Continue the existing exact-prefix, cycle, transfer direction, snapshot consistency, load-budget and replay checks rather than replacing them with nominal happy paths.

The release report must identify the actual environment, test outcome, source/manifest identity and any failed probe/repair. Python tests, browser code, packaging checks and captured assets must include the new fields; an old wheel or screenshot set is insufficient. Rebuild completeness and count semantics need source inspection even when all assertions pass. A human remains responsible for final customer/layout approval.
